# Evaluation Methodology

## Privacy-Preserving Voice Data Assistant — Phase 2

This document describes the evaluation methodology used to benchmark the
reliability, accuracy, and utility characteristics of the voice assistant system.

---

## 1. Principles

1. **Discover truth, not optimism.** Evaluation exists to reveal how the system
   actually behaves, not to produce metrics that look impressive.
2. **Independent ground truth.** Dataset labels are authored manually and
   independently of the implementation. They must never be generated by
   calling `_is_data_query()` or any LLM being evaluated.
3. **Reproducibility first.** Every evaluation run records a `run_id`,
   `git_commit`, Python version, model names, dataset version, and random seed.
4. **Separation of concerns.** Component evaluations test one stage in isolation.
   End-to-end evaluation tests the full pipeline. They produce separate records.
5. **No invented privacy claims.** The system obfuscates voice audio; it does
   not claim to guarantee any specific level of differential privacy or
   k-anonymity. Privacy metrics are placeholders until a speaker-verification
   experiment is conducted (Phase 3).

---

## 2. Dataset

**Location:** `evaluation/datasets/voice_eval_v1.jsonl`

**Format:** JSON Lines, one record per line.

**Fields:**

| Field | Type | Description |
|---|---|---|
| `case_id` | str | Stable unique identifier |
| `category` | str | One of: `data_query`, `non_data_query`, `adversarial`, `ambiguous`, `stt_sensitive`, `boundary` |
| `subcategory` | str | Finer grouping |
| `input_text` | str | Ground-truth natural language query |
| `expected_route` | str | `"tool"` or `"direct"` |
| `expected_tool` | str or null | Tool function name for tool cases |
| `expected_args` | object | Minimal expected tool arguments |
| `notes` | str | Human explanation of the case |

**Versioning:** Dataset filenames include a version suffix (`_v1`, `_v2`, …).
Each evaluation run records `dataset_version` in its metadata.

## 3. Metrics

### 3.1 Word Error Rate (WER)

$$WER = \frac{S + D + I}{N}$$

Where:
- $S$ = substitutions, $D$ = deletions, $I$ = insertions in the hypothesis relative to the reference
- $N$ = number of words in the reference (ground truth)

**Text normalization applied before comparison:**
1. Lowercase
2. Strip punctuation: `.`, `,`, `!`, `?`, `;`, `:`, `'`, `"`, `(`, `)`, `[`, `]`, `{`, `}`
3. Collapse multiple spaces

WER is implemented in `evaluation/metrics/transcription.py` without external dependencies.

### 3.2 Character Error Rate (CER)

Same formula as WER but at character level after normalization.

### 3.3 Routing Metrics (Binary Classification)

Positive class = "tool" (a data query that needs a tool call).

| Metric | Formula |
|---|---|
| Accuracy | (TP + TN) / N |
| Precision | TP / (TP + FP) |
| Recall | TP / (TP + FN) |
| F1 | 2 · Precision · Recall / (Precision + Recall) |
| FPR (false positive rate) | FP / (FP + TN) — measures unnecessary tool calls |
| FNR (false negative rate) | FN / (FN + TP) — measures missed tool calls |

### 3.4 Tool Selection

- **Tool accuracy:** Fraction of tool-routed cases where the correct tool was called
- **Wrong tool rate:** Fraction where a different (valid) tool was called
- **No-tool rate:** Fraction where routing was "tool" but no tool call was made

Tool selection is only evaluated for cases where routing was correct.

### 3.5 Tool Argument Evaluation

Argument accuracy is evaluated at field level, not as exact JSON equality:
- **Semantic match:** All expected fields present with semantically equivalent values (string "10" == int 10, "ACTIVE" == "active")
- **Field accuracy:** Fraction of (expected ∪ actual) fields correctly matched
- Extra unexpected fields in actual count as errors

### 3.6 Transcript Correction

| Metric | Definition |
|---|---|
| `attempt_rate` | Fraction of cases where correction was attempted |
| `acceptance_rate` | Fraction of attempted corrections that were accepted |
| `false_correction_rate` | Fraction of measurable corrections that degraded WER |
| `improvement_rate` | Fraction that improved WER |
| `degradation_rate` | Fraction that degraded WER |

Correction is classified as IMPROVED when `corrected_WER < raw_WER`,
DEGRADED when `corrected_WER > raw_WER`, UNCHANGED otherwise.

### 3.7 End-to-End Task Success

**Strict definition:**
- For `tool` cases: routing correct AND tool correct AND args semantically correct (when expected_args is non-empty) AND connector succeeded AND answer is non-empty
- For `direct` cases: routing correct AND answer is non-empty

### 3.8 Failure Stage Taxonomy

Each failed case is classified at the earliest stage that failed:

| Stage | Description |
|---|---|
| `audio_validation` | File too large, corrupt, or too short |
| `audio_decode` | Cannot decode audio format |
| `obfuscation` | Obfuscation transformation failed |
| `stt` | Whisper transcription raised an exception |
| `stt_abstention` | System correctly refused low-confidence input |
| `transcript_correction` | Correction produced an error or was skipped |
| `routing` | Wrong route (tool vs. direct) |
| `tool_selection` | Wrong tool called |
| `tool_arguments` | Wrong or missing arguments |
| `connector` | Data connector failed or returned no results |
| `answer_generation` | LLM failed to produce an answer |
| `tts` | TTS synthesis failed |

### 3.9 Latency

Reported as percentiles (p50, p90, p95, p99) per stage:
`validation`, `obfuscation`, `stt`, `orchestrator`, `tts`, `total`.

## 4. Evaluation Runners

| Runner | Audio required | LLM required | Scope |
|---|---|---|---|
| `routing_runner.py` | No | Optional | `_is_data_query()` + optionally LLM tool calls |
| `correction_runner.py` | No | Yes | Correction ablation on text input |
| `transcription_runner.py` | Yes (TTS generated) | No | WER/CER on TTS audio |
| `obfuscation_runner.py` | Yes (TTS generated) | No | WER/CER/routing across all 7 obfuscation settings |
| `end_to_end_runner.py` | Yes (TTS generated) | Yes | Full pipeline |

---

## 5. Obfuscation Experiment

Seven configurations are benchmarked:

| Configuration | Method | Shift |
|---|---|---|
| `none` | No obfuscation | — |
| `naive_mild` | Pitch shift (librosa) | mild |
| `naive_medium` | Pitch shift (librosa) | medium |
| `naive_strong` | Pitch shift (librosa) | strong |
| `formant_mild` | WORLD formant-preserving | +2 st |
| `formant_medium` | WORLD formant-preserving | +4 st |
| `formant_strong` | WORLD formant-preserving | +6 st |

**Pareto table** records WER, CER, routing accuracy, and latency for each.
Privacy is marked `not_yet_measured`.

## 6. Privacy Evaluation (Placeholder)

Speaker de-anonymization resistance requires:
1. A speaker verification model (e.g. ECAPA-TDNN from SpeechBrain)
2. A reference speaker embedding
3. A cosine similarity threshold calibrated at a target EER

This experiment is planned for **Phase 3**. Until then, `privacy_metric` is
set to the literal string `"not_yet_measured"` in all result records.

**Claim made here:** The system applies voice obfuscation that changes
fundamental voice characteristics (pitch, formants). We make no claim about
the resulting degree of privacy protection until it is experimentally measured.

---

## 7. Reproducibility

Each evaluation run produces:

```
evaluation/results/<YYYYMMDDTHHMMSSZ>_<run_id>/
  metadata.json   — run_id, git_commit, python_version, model versions, seed
  summary.json    — all aggregate metrics
  cases.jsonl     — one EvalRecord per case (full detail)
  results.csv     — same as cases.jsonl, flattened for spreadsheet use
```

To reproduce a result: use the same `git_commit`, `seed`, `dataset_version`,
and model versions recorded in `metadata.json`.

---

## 8. What Phase 2 Does NOT Claim

- That the system is production-ready
- That obfuscation protects speaker identity (not measured)
- That routing accuracy from `_is_data_query()` is sufficient for deployment
- That transcript correction always helps
- That the evaluation dataset is exhaustive
